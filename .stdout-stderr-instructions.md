# STDOUT / STDERR HANDLING INSTRUCTIONS

## Purpose

Prevent unnecessary context consumption and avoid unsafe/indefinite command execution when working with this project's shell scripts, pipeline processes, and dashboard server.

---

## General Rules

1. **Never run indefinite/long-lived commands merely to observe output.**
   - `dashboard/server.js` is a long-running server. Do not run it in the foreground and wait — always run it in a way that returns control (background execution, or ask the user to run it themselves and report status).
   - Never `tail -f` or equivalent without a bound (use `tail -n <N>` instead).

2. **Prefer bounded, atomic commands.**
   - Use `--no-pager`, `-n`, `| head`, `| tail -n 50`, etc. to limit output size.
   - Avoid dumping entire log files into context; use `grep`/`search_files` to extract only relevant lines.

3. **Large log files live in `output/logs/`.**
   - Files such as `output/logs/full_pipeline_parallel_run.log`, `output/logs/dashboard_server.log`, etc. can be large.
   - NEVER `cat` these files in full. Use `tail -n 100` or `grep <pattern>` to inspect only what's needed.

4. **Background execution for the dashboard server.**
   - When starting `dashboard/server.js` for testing, redirect output to a log file and run detached, e.g.:
     ```
     nohup node dashboard/server.js > output/logs/dashboard_server.log 2>&1 &
     ```
   - Then inspect only the tail of the log file, not the live stream.

5. **Pipeline scripts (`process_video.sh`, `step3_analise_avancada.sh`) may take significant time** (audio extraction, Whisper transcription, AI analysis).
   - Do not block waiting synchronously for full completion in the same command if it risks exceeding reasonable execution time.
   - Prefer running them via the dashboard (which tracks run state) rather than invoking them directly and waiting on stdout, when testing end-to-end behavior.
   - If run directly for debugging, redirect to a log file and poll the tail periodically instead of streaming.

6. **Whisper/ffmpeg output can be verbose.**
   - Redirect to log files under `output/logs/` and grep for errors/warnings/completion markers rather than reading raw streams.

7. **Error diagnosis workflow.**
   - On failure, first `grep -i "error\|fail\|exception" <logfile> | tail -n 30` before reading larger chunks.
   - Only read broader context around a match if the grep result is insufficient.

---

## Summary

Bounded reads. Backgrounded long-running processes. Log files over live streams. Grep before cat.
